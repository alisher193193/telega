# Люди и бригады: проверка и развёртывание

Реализация использует существующие workers, crews, crew_members. Новая таблица
specialties нужна потому, что раньше специальность была только текстом workers.specialty.
Текст сохранён для старых карточек; новые работники ссылаются на specialty_id.
При редактировании старого работника без ссылки нужно выбрать специальность.
Авторитетное название связанной специальности читается из справочника; архивирование
не удаляет связи. Нормализация названий: trim, схлопывание пробелов, casefold.

Права: people.view/manage, specialties.view/manage, crews.view/manage. Старые
workers.view/manage не являются неявными эквивалентами. Bootstrap добавляет новые
права обеим пилотным ролям admin/developer. Ограниченные роли должны получать
явные права. Для выбора специальности/объекта при заполнении работника достаточно
people.manage; это не открывает управление соответствующим справочником.

Все записи выполняются внутри внешней транзакции вызывающего handler.
Общая транзакционная advisory-блокировка people-writes задаёт порядок конкурентных
операций; изменяемые сущности читаются FOR UPDATE. Это сознательная сериализация
малого пилота. Используются существующие directory_mutations, без второй таблицы
квитанций. Хеш включает пользователя, действие и данные; повтор ключа возвращает
существующий результат, изменённый запрос отклоняется. Изменение карточки проверяет
версию снимка, чтобы не затереть чужие правки.

Увольнение завершает текущее участие; восстановление его не возобновляет.
Архивирование бригады завершает её открытые участия; восстановление не меняет историю.
Ставка принадлежит работнику, у бригады общей ставки нет.
История увольнений/восстановлений хранится в audit_logs с old_values/new_values,
автором, временем и общим request_id. Новые сценарии не изменяют и не удаляют аудит.
Дата текущего увольнения при восстановлении очищается; прежнее значение остаётся в аудите.

## Миграция d91f6a20b843

Родитель: c62d4e91b705. По отдельному разрешению миграция применена только
к work_accounting_test. К рабочей базе work_accounting не применялась.

Полный перечень:
- specialties: id UUID PK; name VARCHAR(200); normalized_name VARCHAR(200) UNIQUE;
  is_active BOOLEAN NOT NULL DEFAULT true; created_at TIMESTAMPTZ NOT NULL DEFAULT now().
- workers.specialty_id: nullable UUID FK specialties.id ON DELETE RESTRICT и индекс.
- workers.terminated_at: nullable TIMESTAMPTZ.
- crew_members.joined_on и left_on: nullable TIMESTAMPTZ.
- Частичный UNIQUE uq_crew_members_open_worker на worker_id WHERE left_at IS NULL.
- CHECK ck_crew_members_membership_dates: left_at отсутствует или >= joined_at.
- CHECK ck_crew_members_membership_times: left_on отсутствует либо joined_on задан
  и left_on >= joined_on.
- CHECK ck_workers_worker_rate: base_rate отсутствует либо неотрицателен и не NaN.

Старые DATE-поля сохраняются; новые операции синхронно заполняют DATE в Asia/Almaty
и точные timezone-aware отметки. Для старого участия не придумывается точное время
вступления: карточка показывает имеющуюся календарную дату. Автоматического backfill нет.
Старые миграции не изменяются. Нет UPDATE/DELETE исторических записей в upgrade.

Upgrade аддитивен, но создание UNIQUE/CHECK сканирует и блокирует существующие таблицы.
Некорректные старые данные вызывают отказ всей транзакции. До рабочего применения
нужно проверить данные и иметь резервную копию, согласовать короткое окно обновления.
Downgrade удаляет новую таблицу, связи, точные отметки и ограничения; это потеря новых
данных специальностей/времени, он не безопасен после начала работы. Не выполнять.

## Следующий шаг — только после отдельного разрешения

TEST_DATABASE_URL должен быть экспортирован в shell, без печати значения.
Команда ниже успешно выполнена для work_accounting_test после отдельного разрешения:

```bash
docker compose run --rm --no-deps -e TEST_DATABASE_URL bot python -m app.scripts.migrate_people_test
```

Обёртка проверяет URL (включая отличие от DATABASE_URL), точное имя
work_accounting_test, SELECT current_database() и единственный ожидаемый head.
Только после этого подменяет DATABASE_URL в одноразовом процессе и запускает
alembic upgrade head. Она не читает .env и не меняет рабочий сервис.

После подготовки тестовой схемы прошли 8 интеграционных тестов раздела и полный
набор: 212 passed. Дополнительно проверен аудит создания, редактирования, увольнения
и восстановления в откатываемой транзакции тестовой БД. Повторный запуск:

```bash
docker compose run --rm --no-deps -e TEST_DATABASE_URL bot pytest -q -p no:cacheprovider
```

Новые интеграционные тесты требуют фактическую work_accounting_test.
Обычные тесты откатывают записи. Тест конкуренции использует две независимые
транзакции и сохраняет уникальные тестовые записи для видимости между соединениями;
в finally работник увольняется, справочники архивируются, тестовый пользователь
деактивируется. История и аудит не удаляются физически.

Перед рабочим запуском отдельно согласовать миграцию, bootstrap прав и перезапуск.
Не запускать новый код на старой схеме: ORM workers требует новые колонки.
Не запускать bootstrap автоматически в тестах против рабочей базы.

## Ручная приёмка после развёртывания

1. Проверить видимость разделов с правами просмотра и без прав управления.
2. Создать специальность; проверить повтор с другим регистром/пробелами.
3. Создать работника, пройти Назад, Отменить, главное меню и повторное сохранение.
4. Найти по части ФИО, проверить фильтры статуса и объекта, страницы и карточку.
5. Изменить ставку/объект, сравнить старые и новые значения перед сохранением.
6. Архивировать специальность: старые карточки читаются, новый выбор запрещён.
7. Создать бригаду, добавить человека, проверить запрет второй действующей бригады.
8. Завершить участие; проверить историю, повторно добавить человека.
9. Уволить с причиной, проверить завершённое участие; восстановить без автоматического вступления.
10. Архивировать/восстановить бригаду и проверить сохранённую историю.
11. Проверить HTML в именах, NaN/Infinity/лишние копейки и отсутствие фиктивных финансовых сумм.
